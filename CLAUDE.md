# Hinweise für Claude

Paneldeck ist ein Terminal-Manager für Windows (Rust, egui/eframe, ConPTY via `portable-pty`, Emulation via `alacritty_terminal`).
Überblick: `README.md` (Englisch, Hauptseite) / `README.de.md` (Deutsch; beide synchron halten) – schlanke Startseite (Banner, Download, Erste Schritte, Code-Signatur, Datenschutz, Rechtliches; die Anker `#download`, `#privacy`, `#code-signing-policy` bzw. `#datenschutz-privacy`, `#richtlinie-zur-code-signatur-code-signing-policy` sind für den geplanten SignPath-Antrag vorgesehen, nicht umbenennen) · Anleitungen: `docs/en/*.md` und `docs/de/*.md` (gleiche Seiten, gleicher Aufbau, je Seite Link zur anderen Sprache und zurück zur README; Bilder in `docs/images/` bzw. `docs/images/de/`) – Funktionen, Kommandozeile, Datenordner, Agenten-Schnittstelle usw. stehen dort, nicht mehr in der README · Änderungen: `Changelog.md` (Englisch) / `Changelog.de.md` (Deutsch; beide gleichzeitig pflegen) · manuelle Windows-Tests: `TESTPLAN.md` · Lizenzen: `THIRD_PARTY.md` (Projektlizenz: MIT, `LICENSE`).

## ⚠ Branching- und Release-Strategie (Vorgabe des Nutzers, gilt ab 1.0.0)

Branches: **`develop`** (Standard-Branch auf GitHub, enthält immer alle Entwicklungen) · **`release/x.y`** (ein Branch je Minor-Version, z. B. `release/1.1`; wird nie gelöscht) · kurzlebige Arbeits-Branches. **Es gibt kein `main`.**

1. **Entwicklung** läuft auf Arbeits-Branches von `develop`: **`feature/<name>`** für neue Funktionen, **`fix/<name>`** für Fehlerbehebungen (gerne mehrere zusammengehörige Fixes in einem Branch/PR bündeln, nicht für jeden Kleinkram einen eigenen), `chore/…` für Werkzeuge/Doku. Jeder Branch bekommt einen **Pull Request nach `develop`**, der per **„Squash and merge“** gemergt wird (genau ein Commit je PR, das macht das Cherry-Pick einfach) – von Claude, sobald die CI grün und das Review erledigt ist (siehe Regel 5), sonst vom Nutzer.
   **Große Vorhaben** laufen über einen **Integrationsbranch** `feature/<name>` (neutral benannt): Teil-PRs gehen gegen diesen Branch (Teil-Branches `feature/<name>-<teil>`; Merge nach Regel 5), am Ende ein einziger PR `feature/<name>` → `develop`. Der Integrationsbranch ist wie `develop` geschützt (kein direkter Commit/Push durch Claude). Planungen sind öffentlich: Roadmap, Meilensteine und Issues stehen auf GitHub (Entscheidung des Nutzers 2026-11, keine Geheimhaltung mehr). Die Teile laufen als eigene Arbeits-Branches mit Teil-PRs; gestapelte PRs bauen aufeinander auf, `feature/<name>` wird gelegentlich mit `develop` zusammengeführt. Dokumentation (README, Changelog, Testplan, Release-Notes) bekommt einen eigenen Branch und wird nachgezogen, wenn die Teile gemergt sind (Beispiel: 2.0.0 über `feature/next`).
2. **`release/x.y`** wird von `develop` abgezweigt, wenn ein Release ansteht bzw. kurz bevorsteht. Ab dann landet jede Entwicklung, die zu diesem Release gehört, **sowohl in `develop` als auch in `release/x.y`**: zuerst per PR nach `develop` (Nutzer mergt), dann **per Cherry-Pick** nach `release/x.y` – wieder per PR, den der Nutzer mergt. Cherry-Pick-PR erzeugt `tools/backport.sh <x.y> <name> <commit>… --pr` (Branch `backport/<x.y>/<name>`, `git cherry-pick -x`).
   **Pflicht für Claude (Vorgabe des Nutzers): Cherry-Pick-PRs immer selbst erstellen.** Gehört eine Änderung auch zu einem Release-Branch (Fix für die veröffentlichte Version bzw. Meilenstein = Patch-Release, oder Änderung für ein anstehendes Release mit existierendem `release/x.y`), dann gilt:
   - Im PR nach `develop` steht ausdrücklich „Backport nach `release/x.y` nötig: ja/nein“ (laut Meilenstein des Issues).
   - **Sobald der Nutzer meldet, dass der PR in `develop` gemergt ist, erstelle ich ohne Rückfrage alle nötigen Cherry-Pick-PRs** (`tools/backport.sh <x.y> <name> <commit>… --pr`; die Commits stammen aus `develop` nach dem Merge, vorher `git fetch`) und prüfe danach per Diff, dass der Backport-Branch dem gewünschten Stand entspricht. Betrifft die Änderung mehrere Release-Branches (z. B. ein noch nicht veröffentlichter `release/1.1` und der gepatchte `release/1.0`), gibt es je Branch einen PR.
   - Gemergt wird auch diese PR **immer nur vom Nutzer**. Ich frage nach dem Merge ggf. nach, ob alle Backport-PRs gemergt sind, bevor ein Release vorbereitet wird.
3. **Das Release passiert auf `release/x.y`:** Beim Release wird dort der **Tag `vx.y.z`** gesetzt (x = Major, y = Minor, z = Patch). Aus genau diesem Tag werden `.exe`/Installer/ZIP gebaut und das GitHub-Release erstellt.
4. **Patches** (z. B. `1.0.1`): Fix landet in `develop` **und** in `release/1.0` (Schritt 1 und 2), dann Tag `v1.0.1` auf `release/1.0`, bauen, GitHub-Release.
5. **Keine Release Candidates.** Ist eine Version fertig (z. B. 1.1.0 oder auf Wunsch 1.0.1), wird sie komplett fertig gemacht und direkt veröffentlicht. **Patches gibt es nur für den neuesten Release-Branch.**
6. **Ablauf eines Releases** (alle Schritte außer 3 und 5 ohne Rückfrage vorbereiten, 3 und 5 macht der Nutzer bzw. nur auf sein Wort):
   1. Alles für die Version ist in `develop` **und** (per Backport-PR) in `release/x.y` gelandet; Issues des Meilensteins sind geschlossen; `docs/release-notes/<x.y.z>.en.md` (englischer Release-Text) ist geschrieben.
   2. `tools/release-prep.sh <x.y.z> "<englischer Titel>" --pr` → PR „Release x.y.z vorbereiten“ nach `release/x.y` (setzt Version in `Cargo.toml`/`Cargo.lock`, in beiden Changelogs `WIP` → heutiges Datum, Titel).
   3. **Nutzer mergt diesen PR.**
   4. Auf `release/x.y` (aktuell gezogen, sauber; Changelog-Datum muss **heute** sein, sonst Schritt 2 am Release-Tag wiederholen): `tools/release.sh <x.y.z>` – prüft, testet, baut, setzt das lokale Tag.
   5. Auf Wunsch des Nutzers: `tools/release.sh <x.y.z> --publish` (pusht nur das Tag, legt das Release an) bzw. direkt in Schritt 4 mit `--publish`.
   6. Danach: PR `chore/changelog-<x.y.z>` nach `develop`, der dort nur das `WIP` des Abschnitts `[x.y.z]` in beiden Changelogs durch das Release-Datum ersetzt (`python tools/changelog.py release <x.y.z>` auf einem Branch von `develop`), damit beide Branches übereinstimmen. Meilenstein schließen, nächsten anlegen.
7. **Versionsnummern in `develop`:** `Cargo.toml` auf `develop` trägt die Nummer des obersten `WIP`-Abschnitts; steht dort nur `Fixed`/`Security`, ist es die nächste PATCH-Nummer, kommt eine Funktion dazu, wird der Abschnitt zur nächsten MINOR-Nummer umbenannt (`python tools/changelog.py new <x.y.z>` legt einen leeren WIP-Abschnitt an). Die Changelog-Einträge eines Fixes, der in beiden Branches landet, stehen in den Changelogs beider Branches (bei Backport-Konflikten in `Changelog.md` und `Changelog.de.md` von Hand lösen, danach `python tools/changelog.py check`).
8. **Schutz:** Lokal sperren Git-Hooks (`git config core.hooksPath tools/git-hooks`, in jedem Klon einmal setzen) Commits, Merges und Pushes auf `develop`/`release/*` (Tags sind erlaubt) – **nie mit `--no-verify` umgehen**. Auf GitHub sollen `develop` und `release/*` per Ruleset geschützt werden (nur Pull Requests, kein Force-Push, kein Löschen); das geht auf einem privaten Repo mit kostenlosem Konto nicht, deshalb direkt nach dem Öffentlichschalten einrichten (Issue „Branch-Schutz“).
9. **Aufräumen:** Gemergte oder nicht mehr gebrauchte Branches (remote **und** lokal) und zugehörige Worktrees (`git worktree remove`, `git worktree prune`) werden gelöscht, sobald der PR gemergt ist – ein gemergter Branch bleibt nicht liegen (`release/x.y` und `develop` nie). Vor dem Löschen kurz prüfen, dass nichts Ungemergtes darauf liegt.
10. Veröffentlichte Tags und Release-Dateien werden nie verändert oder verschoben (nur Titel/Text des GitHub-Releases dürfen korrigiert werden).

## Entwicklungsumgebung

- **Entwickelt wird nativ unter Windows 11** (Rust stable, Host `x86_64-pc-windows-msvc`). Früher wurde unter Linux nach `x86_64-pc-windows-gnu` cross-kompiliert;
  `.cargo/config.toml` (mingw-Linker) ist ein Überbleibsel davon und wird nur für diesen Cross-Build gebraucht.
- Bauen/Testen: `cargo build --release` → `target\release\paneldeck.exe` (ca. 1 min); `cargo test --release` (alle Tests laufen parallel stabil).
  Die Windows-Teile (Tray, Hooks, ConPTY, Installer) lassen sich hier direkt ausprobieren – `TESTPLAN.md` Abschnitt 30/31.
- Shells: PowerShell ist die Haupt-Shell, das Bash-Tool ist Git Bash (`sha256sum`, `file` usw. vorhanden). `python3` ist hier nur der Store-Stub, `python` (3.11) funktioniert –
  die Release-Skripte finden das selbst. Python-Skripte immer mit `PYTHONUTF8=1` (sonst cp1252-Fehler an Umlauten). Mehrzeilige Python-Heredocs im Bash-Tool können an Anführungszeichen scheitern → lieber Skript-Datei schreiben und mit `python -I` starten.
- Installiert (winget): GitHub CLI `gh` (angemeldet), NSIS 3.13 (`C:\Program Files (x86)\NSIS\makensis.exe`). In bereits laufenden Shells fehlen sie evtl. im PATH → volle Pfade
  (`C:\Program Files\GitHub CLI\gh.exe`); die Skripte unter `tools/` suchen sie selbst.
- Der Datenordner `paneldeck-data` liegt neben der `.exe` (also unter `target\release\`); er sowie `target/` und `dist/` sind git-ignoriert. Suchreihenfolge ab 2.1.0: `--data-dir` > `PANELDECK_DATA` > `paneldeck-data` neben der .exe (wenn beschreibbar) > `%APPDATA%\Paneldeck` > aktuelles Verzeichnis; `--profile <name>` = Unterordner `profiles\<name>` (`src/paths.rs`, Kommandozeile `src/cli.rs`, Hilfetext `src/help.rs`). Für Tests eigene Datenordner per `--data-dir`/`--profile` statt des echten nehmen.
- **Plattform-Schicht (ab 2.4.0, #148):** Windows-spezifischer Code liegt in `src/platform/` (chrome, window, process, tray, notify, console, conpty, taskbar, clipboard, keyboard, open, fs, fonts, secret, registry; WinHTTP in `llm/http/winhttp.rs` und `app/update/http/winhttp.rs`), außerhalb von Windows Platzhalter. Die CI baut und testet zusätzlich auf Linux und macOS (`build-test-unix`). **Aufrufer-Zuordnung unter Linux/macOS (#149/#150, ab 2.5.0):** `platform::unix_proc` – Socket-Besitzer über `/proc/net/tcp` + `/proc/<pid>/fd` bzw. libproc, Prozessbaum ab der Shell, zur Sitzung gehört ein Aufrufer nur über den Baum; der Hub ist unter Linux Child Subreaper (`become_subreaper`, in `main.rs`), losgelöste Nachfahren landen unter ihm und gelten als `orphan` (unter Unix immer eingeschränkt, `attribute`); die Markierung `PANELDECK_SESSION_JOB` in der Umgebung kann nur einschränken, nie eine Sitzung geben; macOS ohne Subreaper: Abriss bei launchd nach dem Hub-Start = `orphan`; nicht zu bestimmen → abgewiesen (Tests in der Linux-/macOS-CI, Smoke unter Linux: `tools/smoke-linux.py` unter Xvfb im Job `package-linux`).
- `.gitattributes` erzwingt LF für `*.sh` und `tools/git-hooks/*` (CRLF bricht Git Bash). Skripte sind im Index ausführbar (`git update-index --chmod=+x`), Windows meldet sonst Modus-Änderungen.

- **Maus/Tastatur/Screenshot:** `. tools\gui-test.ps1` (Win32: `Focus`, `Top`, `Click`, `Drag`, `Wheel`, `Press 'ctrl+x'`, `TypeText`, `MoveAbs`, `ShotPW`). `ShotPW` nutzt PrintWindow und funktioniert auch bei verdecktem Fenster.

- **UI-Tests – Regeln (Vorgabe des Nutzers):**
  - **Immer nur eine Paneldeck-Testinstanz gleichzeitig** (parallele Instanzen stehlen sich gegenseitig den Fokus und stören den Nutzer). Ohne Bestätigung nur Unit-Tests, headless-egui-Tests (siehe `src/app/planning_ui/*_tests.rs`), `cargo build/test --release` und `tools\smoke-mcp.ps1` (unter der Sperre). Unterstützende Agenten testen die Oberfläche nicht selbst, sondern liefern die UI-Schritte (Ausgangszustand, Eingabe, erwartetes Ergebnis) als Liste für den gebündelten Lauf.
- Windows-PowerShell 5.1: `Set-Content -Encoding UTF8` und `Process.StandardInput` schreiben ein BOM; JSON-Leser im Projekt tolerieren es (`state::strip_bom`).

## Changelog: Keep a Changelog 1.1.0 (Vorgabe des Nutzers)

Es gibt **zwei Changelogs mit gleichem Gerüst** (Entscheidung des Nutzers): **`Changelog.md` (Englisch)** folgt https://keepachangelog.com/en/1.1.0/ und verweist auf https://semver.org/spec/v2.0.0.html, **`Changelog.de.md` (Deutsch)** folgt https://keepachangelog.com/de/1.1.0/ und verweist auf https://semver.org/lang/de/; jede Einleitung nennt die andere Fassung. Geprüft wird mit `tools/changelog.py` (`python tools/changelog.py check`; CI und `release.sh` rufen es auf und brechen bei Fehlern ab): Format jeder Datei **und** Gleichlauf – dieselben Versionen in derselben Reihenfolge, dieselben Daten/`WIP`/`[YANKED]`, je Version dieselben Typ-Überschriften und identische Link-Definitionen am Ende.
- **Jede Änderung, die Nutzer betrifft, wird gleichzeitig in beide Dateien eingetragen** (im selben Commit/PR; der englische Eintrag ist eine natürliche Übersetzung des deutschen bzw. umgekehrt, UI-Begriffe wie in der englischen Oberfläche, Code/Tasten/Links identisch, `Ctrl`/`Shift`/`Alt` statt `Strg`/`Umschalt`).
- **Aufbau:** `# Changelog`, Einleitung mit Verweis auf Keep a Changelog und Semantic Versioning, dann die Versionen **neueste zuerst** als `## [X.Y.Z] - JJJJ-MM-TT` (ISO-Datum) bzw. `## [X.Y.Z] - WIP` für noch nicht veröffentlichte Versionen (**kein `[Unreleased]`**, Entscheidung des Nutzers), am Dateiende je eine Link-Definition `[X.Y.Z]: …/compare/v<vorherige>...v<X.Y.Z>` (bei WIP `...HEAD`). Zurückgezogene Versionen bleiben stehen und bekommen `[YANKED]` hinter dem Datum.
- **Datum** = Datum des Git-Tags der Version (Entscheidung des Nutzers), nicht das spätere Veröffentlichungsdatum des GitHub-Releases; `changelog.py release` ersetzt `WIP` durch das heutige Datum (in der Release-Vorbereitung, am Release-Tag); `release.sh` bricht ab, wenn das Datum nicht heute ist.
- **Änderungstypen** (englische Überschriften wie auf der Seite, genau in dieser Reihenfolge, leere weglassen): `### Added` (neue Funktionen) · `### Changed` (Änderungen an bestehenden Funktionen) · `### Deprecated` (bald entfernt) · `### Removed` (entfernt) · `### Fixed` (Fehlerbehebungen) · `### Security` (Sicherheitslücken/Härtung). Einträge in `Changelog.md` englisch, in `Changelog.de.md` deutsch (die Typ-Überschriften bleiben in beiden englisch), für Menschen geschrieben (kein Commit-Log), Veraltetes/Entferntes/Inkompatibles immer nennen.

## Agenten-Schnittstelle (MCP)

`paneldeck.exe mcp` = stdio-Brücke zur laufenden Instanz (Port + Token aus `ipc.json` im Datenordner), Stufe in den Einstellungen: Aus (Standard) / Lesen / Steuern.
- `src/mcp.rs`: Protokoll (JSON-RPC, Versionen), Werkzeugliste (`tools()` mit Mindeststufe), Brücke `run_bridge`, `key_bytes`, `base64`, Protokoll-Hilfen, `unregister_if_ours` (Deinstallation). Kennt kein egui.
- `src/hooks.rs`: `McpJob`/`mcp_rx`, `handle_mcp` (Token + **Stufe im Hub prüfen**, nicht erst in der Brücke), `call_mcp`. Die Stufe steht in der globalen `mcp::LEVEL` (UI schreibt sie jedes Frame).
- `src/app/mcp.rs`: Ausführung in der UI-Schleife (`poll_mcp`, pro Frame; Wartendes wie `run_command`/`wait_for_status`/`screenshot` bleibt in `McpState::pending`), Einstellungs-Tab, Seitenleisten-Chip.
- `src/terminal.rs`: `tail_text`, `screen_text`, `lines_abs`, `send_text_agent` (ohne Broadcast), Zähler in `ShellState`, `quiet_for`. `src/osc.rs`: `feed_at` (Positionen) – der Datenblock wird an den Sequenzen geteilt, damit die Prompt-Zeile exakt stimmt.
- `src/sysprompt.rs` (Untermodul von `mcp`): Systemprompt für `initialize`/`instructions` (eingebaute Vorlage EN/DE, eigene `system-prompt.md` im Datenordner, höchstens 64 KB, Platzhalter `{{tools}}`/`{{level}}`/`{{mode}}`/`{{version}}`); Oberfläche in `src/app/sysprompt_ui.rs`. Jedes neue Werkzeug braucht eine Kurzbeschreibung in beiden Sprachen (`short_desc`, per Test geprüft).
- Brücke findet ihren Hub: `mcp --data-dir/--profile` > Hub des Terminals, aus dem sie startet (`PANELDECK_HUB_DATA`/`PANELDECK_HUB_BASE`, intern) > normale Datenordner-Suche (`paths::bridge_dir`). Instanzen mit Profil/Datenordner registrieren sich als `paneldeck-<profil>` bzw. `paneldeck-<hash>` (`src/launch.rs`); Autostart je Instanz als Run-Wert `Paneldeck (<…>)`, Kontextmenü nur einmal (`src/integration.rs`).
- Sicherheitsregeln (nicht aufweichen): Aus als Standard; kein Schreiben in die eigene Sitzung des Agenten (`PANELDECK_SESSION` der Brücke); nichts bei offener Freigabe-Frage; Schließen nur selbst angelegter Sitzungen (außer Einstellung); nie Admin-Profile, nie eigene Programme/Argumente; Antworten kennzeichnen Terminalinhalt als nicht vertrauenswürdig. Umweg-Schutz für Chats: Eine von einem Agenten ausgelöste Chat-Runde schreibt in keine Sitzung ihrer Kette (`origin_sessions`, transitiv nur über Chats) und startet keine Claude-Sitzungen und keine MCP-Brücke (`spawn_forbidden`, nach bestem Bemühen).
- **Agenten-Kette (ab 2.3.0, #152, `src/app/taint.rs`):** Eine Sitzung, die ein Agent mit eigener Kette anlegt (`create_session`, `paneldeck --open` aus einer Sitzung), erbt dessen Kette samt ihm (`state.json` `agent_chain`); wer per MCP in eine Sitzung schreibt, gibt seine Kette weiter. Kein Agent schreibt in eine Sitzung seiner Kette, benennt sie um, zeigt oder schließt sie (`forbidden`). Sitzungen eines vom Nutzer gestarteten Agenten (ohne Kette) sind nicht markiert. Der Hub ermittelt den Aufrufer selbst (TCP-Tabelle, Prozess) und ordnet ihn über das **Job Object** der Sitzung zu (#168, `src/platform/process.rs`, Patch in `vendor/portable-pty`; jede Shell läuft in einem eigenen Job, `CREATE_BREAKAWAY_FROM_JOB` schlägt fehl), der Prozessbaum ist Rückfallweg; in WSL zählt `PANELDECK_SESSION` nur mit `PANELDECK_SESSION_KEY`. **Grenze (so auch in der Doku):** Die Zuordnung über Job/Prozessbaum ist keine Grenze gegen bösartigen Code unter demselben Benutzer (Attribut PARENT_PROCESS, DuplicateHandle, WMI/schtasks/COM); die Ketten-Regeln schützen vor gelenkten Agenten (Prompt Injection), nicht vor feindlichen lokalen Programmen. **Ab 2.3.1:** Der Job einer geschlossenen oder neu gestarteten Sitzung bleibt im Hub (`closing::Retired`), solange darin Prozesse laufen; ein übrig gebliebener Prozess zählt als diese Sitzung samt ihrer Kette (`taint::set_retired`), gibt sie weiter, und von ihm angelegte Sitzungen gehören niemandem. Ca. 6 s nach Schließen/Neu laden meldet ein Hinweis noch laufende, in der Rückfrage nicht genannte Prozesse („Alle beenden“). Die Baum-Regel „verwaist“ (Elternkette bricht nach dem Hub-Start ab) gilt nur noch, wenn eine laufende Sitzung keinen Job hat; dann `forbidden` für Schreiben in Claude-Sitzungen/Chats und das Starten von Claude-Sitzungen, Chats oder der MCP-Brücke. Kinder einer geschlossenen Ersteller-Sitzung gehören niemandem (`parent: null`, `created_by_agent: true`); schließen darf sie ein Agent nur mit der Einstellung „Agenten dürfen auch fremde Sitzungen schließen“. Ein aufgeschobenes `create_session` (wartet auf die WSL-Ordnerprüfung) prüft die Stufe erneut. **Ab 2.3.2 (#260/#245):** Hook-Meldungen tragen `PANELDECK_SESSION_KEY` und zählen nur für den laufenden Start (`hooks::admit`, `ConvBinding`): Konversations-IDs bindet nur die beim Start übergebene ID (`--session-id`/`--resume`) bzw. ein SessionStart, SessionEnd löst die Bindung; Meldungen ohne Key (ältere globale Hooks) nur für den Status; `--safe-mode`-Starts ignorieren Hooks. (Startregeln ab 2.4.1 siehe unten.) **Ab 2.4.0 (#282, `src/app/claude_status.rs`):** Status-Rückfall ohne passende Hook-Meldung über Transkript-Position (`Usage::ended_after`, nie Uhrzeitvergleich) und Bildschirm (`hooks::screen_hints`: Spinner, offene Frage) – nie „bereit“ ohne Beleg oder bei sichtbarer Frage; „Claude beendet“ nur bestätigt (Vordergrund der Shell leer, `shell_is_idle`), ein OSC-Prompt allein hebt nichts Sicherheitsrelevantes auf; die Warteschlange läuft nur für den vom Hub gestarteten Claude nach einer per UserPromptSubmit eröffneten Runde und pausiert, wenn Claude endet. Nur Hook-Ereignisse eintragen, die mindestens so alt wie `SessionEnd` sind (unbekannte Namen können ältere Claude-Versionen die ganze Settings-Datei verwerfen lassen). **Ab 2.4.1 (#302):** Nur eine Konversation, die der Sitzung gehört (`ConvBinding::own`: die per `--resume` übergebene ID, sonst – neuer Start ohne ID oder `--continue` – der erste SessionStart des gestarteten Claude, dazu `/clear`/`/resume`/Komprimierung des gestarteten Claude), wird nach `claude_session`/`claude_started`/`transcript` geschrieben (`Entry::note_conversation`); nur `prompt_input_exit`/`logout`/`bypass_permissions_disabled` beenden die Kette (`hooks::session_end_is_quit`), ein danach von Hand gestarteter Claude (Quelle `startup`) zählt nur für den Status. Die Startentscheidung ist `session_settings::launch_start` nach „Fortsetzen nach Neustart“ (`SessionMeta::resume_mode`, `state.json` `claude_resume_mode` off/continue/pick, `claude_continue` wird für ältere Versionen mitgeschrieben): neuer Start = nur `claude` + Hook-`--settings` (kein `--session-id` mehr); „Fortsetzen“ ab Neu laden/Neustart/Programmstart immer `--continue` (Nutzerentscheidung: auch für Agenten-Sitzungen und mehrere Sitzungen im selben Ordner – die neueste Konversation des Ordners kann fremd sein, so dokumentiert), nur wenn es im Ordner eine Konversation gibt (`session_settings::folder_has_conversation`: Windows Transkript unter `projects/<slug>`, WSL nur `claude_started`); „Auswählen“ zeigt vorher die Auswahl (`src/app/conv_pick.rs`, Suche im Hintergrund, WSL über `\\wsl.localhost`, eine zur Zeit, Sitzung bis dahin ohne Prozess: `Entry::pick_pending`) und startet mit `--resume <id>` oder neu; ein Start ohne Auswahl (z. B. künftig über MCP) beginnt in diesem Modus neu. **Bekannte Grenzen:** Nach einem Neustart des Hubs (z. B. Update) sind übrig gebliebene Prozesse aus Sitzungen der vorigen Instanz nicht mehr zuordenbar (die Jobs liegen nur im Speicher) und gelten als normale externe Aufrufer. Die Ketten-Regeln beschränken nur MCP-Werkzeuge – ein Agent mit Stufe Steuern, der Shell-Befehle ausführen kann, kann im Terminal trotzdem z. B. `claude` mit beliebigen Schaltern starten; die `claude_flags`-Erlaubnisliste von `create_session` ist keine Sandbox.
- `run_command`-Grenzen: PowerShell/cmd liefern nur `quality: approx`; Exit-Code bei cmd `null`; PowerShell-Exit-Code kann nach einem nativen Programm veraltet sein; langsame Prompts (Git Bash) werden über die Echo-Zeile abgegrenzt. Das Echo eines langen, umbrochenen Befehls wird über seinen Text gefunden (`terminal::find_echo`, ohne Leerraum verglichen), nicht über das WRAPLINE-Flag – ConPTY/PSReadLine zeichnen die Eingabezeile oft mit eigenen Zeilenvorschüben neu, dann fehlt das Flag (#122). Mit dem System-ConPTY (conhost) kommt nach einer Zeile in genau Terminalbreite bei Git Bash der Zeilenumbruch erst nach OSC 133;A: Die Marke ist dann vorläufig (`ShellState::mark_open`), `run_command` nimmt `prompt_start()` (#231; Rest-Macke #264). Prompt-Marken und laufende `run_command`-Starts folgen dem Neuumbruch beim Resize (`Session::pin_abs`/`AbsPin`, #246; im Alternativbildschirm nicht).
- **Chats mit lokalen Modellen (ab 2.2.0, #63):** Sitzungsart `SessionKind::Chat` neben Terminals (`state.json` `kind`/`chat` = `ChatMeta { server, model }`, Verlauf in `chats/<id>.json`).
  - `src/llm/` (kein egui, keine App): `http` (WinHTTP asynchron, eigene Handles, kein Proxy, keine Weiterleitungen/Cookies/Auto-Anmeldung, Zertifikate immer geprüft ohne erzwungene Sperrprüfung, Zeitlimits 10 s/30 s/300 s, Größengrenzen), `net` (URL-Zerlegung und Host-Regel: nur localhost/127/8, ::1, 10/8, 172.16/12, 192.168/16, 169.254/16, fc00::/7, fe80::/10; mehrdeutige Zahlenformen abgelehnt; Namen vor JEDER Anfrage aufgelöst, alle Adressen müssen erlaubt sein, geprüfte IP wird festgelegt, Gegenstelle nach dem Verbinden geprüft), `ollama`/`openai` (Adapter, NDJSON bzw. SSE), `config` (`settings.json` `llm_servers`: `LlmServer`/`LlmModel`, tolerant, unlesbare Einträge bleiben roh erhalten), `secret` (DPAPI `CryptProtectData`, aktueller Benutzer; Base64 des Blobs, nie Klartext), `tokens` (Schätzung, Kürzen auf das Budget), `error` (Texte EN/DE). Neue Netzwerkziele nur über diese Host-Regel – nie aufweichen.
  - `src/chat/` (kein egui): `store` (Datenformat, tolerantes Laden, atomares Speichern, `.defekt-`/`.orphan-`-Sicherungen, Löschen beim Schließen), `backend` (`ChatBackend`/`TurnEvent`, `EchoBackend` für Tests), `llm_backend` (Anfrage bauen: Systemprompt für die Stufe des Modells + Kontextzeile Projekt/Ordner, Verlauf, Kürzung mit 25 % Antwort-Reserve, `num_ctx` bei Ollama automatisch nach `llm::config::auto_context`: (Systemprompt + Werkzeuge + 4096) / 0,75, Zweierpotenz, 8192–32768, höchstens die Länge des Modells; eigene Angabe bleibt, Hinweis bei zu klein), `logic` (Bearbeiten/Neu erzeugen/Wiederholen), `session` (`ChatState`: Verlauf, Streaming, Werkzeug-Schleife `tool_step`, Freigaben, Schritte, Kontext-Platz für Ergebnisse), `tools` (`ToolPolicy`: Werkzeuge nach Stufe/Modus/abgewählt, Prüfung beim Ausführen, `NO_APPROVAL` = `wait_for_status`/`focus_session`, Ergebnis-Kürzung auf höchstens 16 KB mit erhaltenem Ende bei Terminalausgabe, Screenshots ohne Bild, kompakte Beschreibungen nur für Chat-Modelle, Umweg-Schutz `proxy_forbidden` vor der Freigabe), `driver` (`drive`/`ChatToolHost`: führt die Schleife je Bild weiter, testbar mit Ersatz-Hub). Oberfläche: `src/app/chat_ui.rs` (Chat-Bereich), `src/app/models_ui.rs` (*Einstellungen → Modelle*, Dialog *Neuer Chat*).
  - **Werkzeug-Schleife** läuft in `ChatState`/App, nicht im Backend-Faden: Werkzeugaufrufe werden im **Hauptdurchlauf** (`wins.cur == 0`) über den MCP-Ausführer (`src/app/mcp.rs`) ausgeführt, mit **Aufrufer = Chat-Id** (`how = "chat"`) – damit gelten alle Sicherheitsregeln oben (nie eigene Sitzung, Kinder gehören dem Chat, nichts bei offener Freigabe-Frage …). Die **Stufe je Modell** (`LlmModel::level`, Standard **Aus**; ohne `level_chosen` gilt sie überall als Aus, der erste Chat fragt einmalig) ist **unabhängig** von `mcp::LEVEL` (die gilt nur für externe Agenten); Stufe/abgewählte Werkzeuge/Expertenmodus werden beim Ausführen erneut geprüft. Schreib-Werkzeuge (alle ab Steuern außer `NO_APPROVAL`) warten mit `ask_write` auf Freigabe in der Oberfläche (Erlauben / Immer für diesen Chat / Ablehnen; „Immer“ nur mit Ziel `session` als Zahl, nie für `create_session`, gespeichert als `always_allow` in `chats/<id>.json`); externe Agenten können sie nie freigeben. `max_steps` je Antwort (auch abgewiesene Aufrufe zählen), danach *Weiter*; kein Aufruf ohne Platz für sein Ergebnis (sonst Pause „Kontext voll“, *Weiter* überspringt die wartenden Aufrufe). Token-Schätzung vorsichtig (`llm::tokens`), abgeglichen mit den echten Zahlen des Servers (`token_scale`); Ollama bekommt `num_ctx` und `num_predict`.
  - MCP für externe Agenten: `list_sessions` mit `kind`/`model`, `read_chat` (Lesen), `list_models` (Lesen, nie Schlüssel oder volle Adressen), `send_chat_message` (Steuern), `create_session` mit `kind: "chat"`, `server`, `model`; Chat-Status `ready`/`working`/`approval`; Fehlercodes `not_a_terminal`, `not_a_chat`, `busy` (Streaming oder Nutzer bearbeitet), `permission_pending` (Freigabe oder Stufen-Frage offen), `no_model`. Ein von einem Agenten angelegter Chat darf nie in die Sitzung dieses Agenten schreiben (Umweg-Schutz). Chat-Inhalt wird wie Terminalinhalt als nicht vertrauenswürdig gekennzeichnet.
- **Mehrere Fenster** (`src/app/multiwin.rs`): weitere Fenster sind egui-Viewports im selben Prozess; `enter`/`leave` tauschen die `WinView` mit den Feldern der App. Die Tauschliste (`view_fields!`/`swap_fields!`) zerlegt `WinView` ohne `..` – ein vergessenes Feld ist ein Übersetzungsfehler. In weiteren Fenstern werden egui-`Memory::data` (je Fenster eigene `IdTypeMap`) und Animations-Ids (`style::salted`, über `style::set_id_salt`) getrennt; neue Animationen/Panel-Ids, die in mehreren Fenstern vorkommen können, über `style::anim`/`style::salted` laufen lassen. Alles Globale (Hooks, MCP, Tray, Speichern) läuft nur mit dem Hauptfenster in den Feldern (`wins.cur == 0`).

- **Veröffentlichte Versionen werden nie verändert:** kein Tag verschieben, keine Release-Dateien austauschen; ein Fehler wird mit der nächsten PATCH-Version behoben.
- **Veraltete API zuerst als „deprecated“ im Changelog** (in einer MINOR-Version) markieren und erst in der nächsten MAJOR-Version entfernen.
- **`0.y.z` ist „initiale Entwicklung“** (alles darf sich ändern) – das galt bis 0.20.0. Ab **1.0.0** ist die öffentliche API oben verbindlich; vor 1.0.0 trotzdem schon so versionieren (PATCH = nur Fehlerbehebungen).
- Bis einschließlich 0.20.0 gab es PATCH-Versionen mit neuen Funktionen (0.15.2–0.15.5, 0.17.1–0.17.3); das ist in der initialen Entwicklung erlaubt, wiederholt sich aber nicht.

- **`tools/release.sh <version> [--publish] [--skip-smoke] [--no-git] [--ignore-defender]`** (aus Git Bash: `bash tools/release.sh …`) – läuft unter Windows und Linux (`tools/common.sh` erkennt die Umgebung). **Es committet nicht**, und es läuft nur auf `release/<x.y>` bei sauberem Arbeitsbaum und Stand == `origin/release/<x.y>` (Prüfungen: Branch, Cargo-Version, beide Changelogs mit heutigem Datum und im Gleichlauf, englischer Text, Titel, Lizenztexte):
  Tests → Release-Build → `dist/paneldeck-<v>.exe` → Installer (NSIS, Icon aus `assets\icon.ico` via `MUI_ICON`/`MUI_UNICON`) → SHA-256 + Pfad-Prüfung → **Defender-Prüfung** (siehe unten) → **Smoke-Test** (`tools/smoke-mcp.ps1`, nur Windows) → **Update-Test** (`tools/update-test.ps1`) → Tag `v<v>` (lokal) → ZIP + Release-Texte.
  - `--no-git`: Probelauf auf jedem Branch (nur bauen/packen, kein Tag/Push, Changelog nur auf Format geprüft).
  - `--publish`: zusätzlich **nur das Tag** pushen und das GitHub-Release anlegen (`gh release create`, Titel/Text aus `dist/gh-title-<v>.txt` / `dist/gh-notes-<v>.md`, Assets: portables ZIP + Installer + `dist/sums-<v>/SHA256SUMS.txt`). Normales Release; Pre-release nur bei Versionen mit `-` (Release Candidates nutzen wir nicht).
  - `--ignore-defender`: trotz Defender-Treffer weitermachen – **nur nach ausdrücklicher Zustimmung des Nutzers**.
- **⚠ Defender-Prüfung vor jedem Release (Vorgabe des Nutzers, 2026-11-15):** Solange die Release-Dateien unsigniert sind (Issue #5), erkennt Microsoft Defender unsignierte Builds immer wieder fälschlich als Schadsoftware (bisher `Trojan:Win32/Bearfoos.A!ml`, ML-Fehlalarm, schwankt von Build zu Build). Deshalb werden **vor jedem Release `paneldeck.exe` und der Installer `Paneldeck-Setup-<v>.exe` geprüft** – `release.sh` macht das automatisch mit `tools/defender-scan.ps1 <Dateien>` (scannt Kopien unter `%TEMP%` ohne Entfernen; Exit 0 sauber, 1 Treffer, 3 Prüfung nicht möglich) und hält bei einem Treffer **vor Tag und Veröffentlichung** an. **Bei einem Treffer hilft Claude dem Nutzer jedes Mal, das Microsoft-Formular auszufüllen** (https://www.microsoft.com/en-us/wdsi/filesubmission?persona=SoftwareDeveloper; einreichen und anmelden tut der Nutzer selbst): Felder *Microsoft Defender Antivirus (Windows)* · *Incorrectly detected as malware/malicious* · Detection name, Definition version und SHA-256 aus der Skript-Ausgabe · die erkannte Datei aus `dist/` hochladen · „Additional information“ englisch: Projektbeschreibung (Open Source, MIT, Repo-Link), dass es ein unsignierter, nicht gepackter Build aus dem öffentlichen Repository ist, was das Programm tut (Shells/ConPTY, lokale MCP-Schnittstelle, Autostart/Kontextmenü nur auf Wunsch, keine Downloads außer dem Self-Update von GitHub auf Wunsch) und dass eine Code-Signatur (über SignPath Foundation) geplant, aber noch nicht beantragt ist. Danach Release erst nach Rücksprache fortsetzen (neu prüfen oder `--ignore-defender`).
  - **Testbuilds und Defender:** Der Nutzer hat eine Defender-Ausnahme **nur für `E:\paneldeck-test`** eingerichtet (bis zur Code-Signatur). Builds für Tests dort hinein (`CARGO_TARGET_DIR=E:\paneldeck-test\target-<name>`), Testinstanzen von dort starten; die Ausnahme nie ausweiten, ohne den Nutzer zu fragen. **Release-Läufe (auch `--no-git`) deshalb aus einem Worktree unter `E:\paneldeck-test`** (z. B. `git worktree add E:\paneldeck-test\rel-<x.y> release/<x.y>`; dann liegen `target/` und `dist/` in der Ausnahme) mit `PANELDECK_TEST_ROOT=E:\paneldeck-test` (Temp-Ordner von Smoke- und Update-Test); `tools/defender-scan.ps1` prüft bewusst Kopien außerhalb der Ausnahme.
  - **Nie zwei Release-Läufe parallel** (ein per Tool „gestoppter“ Lauf kann im Hintergrund weiterlaufen – vorher mit `ps -W`/`tasklist` prüfen) und nach dem Veröffentlichen die Dateien aus dem Release herunterladen und per SHA-256 mit `dist/` vergleichen.
- **GitHub Actions** (`.github/workflows/`): `ci.yml` prüft jede PR und jeden Push auf `develop`/`release/**`/`feature/next` (Build, Tests, Changelog-Format, Lizenztexte, Shell-Syntax; Windows-Standard-Runner, Actions per Commit-SHA gepinnt). `ci.yml` hat dazu den Job `package-linux` (Linux-Pakete bauen und prüfen). `release-build.yml` baut bei einem Tag `vX.Y.Z` Installer und ZIP in der Cloud (ohne Smoke-Tests, keine Desktop-Sitzung), erzeugt SHA-256 und einen Herkunftsnachweis (Attestation) und legt sie als Artefakte ab – **es veröffentlicht nichts**; die offiziellen Release-Dateien kommen bis zur Code-Signatur weiter aus `tools/release.sh … --publish`. Der SignPath-Signaturschritt ist dort vorbereitet (auskommentiert; Issue #5). Neue Actions immer mit voller Commit-SHA pinnen.
- `tools/backport.sh <x.y> <name> <commit>… [--pr]` überträgt Commits aus `develop` per Cherry-Pick als PR nach `release/x.y` (siehe Strategie, Punkt 2).
- Remote `origin` = `github.com/zibbozz/paneldeck` (Branches `develop` = Standard, `release/x.y`; kein `main`). Die Historie beginnt mit 1.0.0; die frühere Entwicklung (0.x, anderer Projektname) liegt in einem getrennten, privaten Archiv.
- Push von Arbeits-Branches und PRs gehören zum normalen Ablauf (Regel 5); **Tags und Releases** sind nach außen sichtbar → **nur auf ausdrücklichen Wunsch** (`--publish` nicht von selbst setzen).

## Bekannte Stolpersteine

- NSIS findet Pfade mit `/` nicht → `abspath` in `tools/common.sh` liefert unter Windows Backslashes.
- `tools/release_notes.py` liest/schreibt explizit UTF-8; ohne das bricht Python unter Windows ab.
- Die Setup-`.exe` aus dem Probelauf enthält denselben Code wie die veröffentlichte, ist aber nicht byte-identisch (Build ist nicht reproduzierbar) – Release-Assets nur aus dem echten Lauf hochladen.
- Das Hub-Fenster ist transparent; Screenshots per Bildschirmkopie zeigen dann, was dahinter liegt → `ShotPW` oder das MCP-Werkzeug `screenshot` nehmen.
- Ein im Tray versteckter Hub ist „minimiert + ohne Taskleistenbutton“ (`IsWindowVisible` bleibt wahr; `IsIconic` prüfen).
